# Memoria del frontend

Historial de decisiones y limitaciones reales, una línea por tarea cerrada (la más reciente al final).
Antes de programar, lee también `AGENTS.md`, `features.md` y `docs.md`.

Cómo registrar una tarea: agrega al final una línea `- Tema (AAAA-MM-DD): qué se hizo, cómo se validó y qué
limitación queda`, sin datos personales, claves ni textos de excepciones.

- Landing y cuentas (2026-10-05): landing de TechFix.AI en React y pantallas de registro, acceso, recuperación y restablecimiento siguiendo los prototipos de Figma; contraseña con requisitos en vivo; modo demostración sin `VITE_API_URL`.
- Portal y panel del taller (2026-10-05): portal del cliente (tickets y asistente) y panel del taller con datos de demostración en memoria; protección de rutas por rol con `sessionStorage` (solo rol, nombre y correo).
- Chat con los patrones (2026-10-07): el asistente envía `POST /api/chat` con la cookie de sesión y el patrón elegido (Jerárquico, Orquestador o Red descentralizada); el patrón queda fijo por conversación; si la sesión vence, lleva al acceso y vuelve al chat.
- Mismo origen en producción (2026-10-07): login y chat usan siempre `/backend/*` en producción para que la cookie HttpOnly sea del mismo sitio; `public/_redirects` reenvía a Render en Netlify.
- Mis Tickets (2026-10-13): la vista carga los tickets del cliente desde `/api/customer/tickets` (solo lectura). Limitación: `consultation.test.jsx` falla desde este cambio.
- Código en inglés (2026-10-13): nombres e identificadores en inglés; comentarios en español; textos de la interfaz en español.
- Estilos generales (2026-10-13): `src/styles/` con tokens, base y componentes compartidos; `styles.css` queda para la landing y `app.css` para el portal y el taller.
- Repositorio propio (2026-10-20): el frontend se separó del monorepositorio con su historial (sin archivos `.env`); producción en Vercel (`techfixai.vercel.app`). Limitaciones: Vercel debe apuntar a este repositorio y el proxy `/backend/*` no está en un `vercel.json`; el arreglo de la negrita del chat (PR #30 del repositorio anterior) aún no se trae.
- Clean Architecture (2026-10-21): capas `domain` (dinero, validaciones, tickets, cuenta), `shared` (UI sin estado, estilos, URL de la API), `state` (store, datos de demostración, sesión), `features` (auth, chat, tickets, workshop, landing, help) y `app` (rutas y layouts); prueba de dependencias entre capas y unitarias de dominio. Se trae la negrita del chat (`RichText`). Vitest: 72 aprobadas y 1 falla previa (`consultation.test.jsx`). Limitación: el taller sigue con datos de demostración.
- Limpieza (2026-10-21): piezas comunes de los dos chats en `ChatParts.jsx` (título, encabezado, mensaje del usuario, «escribiendo», hora); «Mis Tickets» vuelve a mostrar los tickets del modo demostración (incluidas las consultas del chat) y «Presupuesto: Por cotizar». Vitest: 73 aprobadas, sin fallas. Sin exportaciones ni archivos sin uso.
- Identidad Banco (2026-10-30): nueva marca, logo, tipografías y sistema (`design/`); navegación con franja superior y barra inferior en celular; la cola pasa a tablero por estación con «Mostrar más» en vez de paginación, el inventario a estantes con medidor de stock, y el asistente a chat con etiqueta lateral. Sin cambios en dominio, estado, clientes de API ni rutas. Limitaciones: se validó en modo demostración, sin backend; bajo carga, algunas pruebas superan el tiempo por defecto de 5 s de Vitest.
- Transcripción de audio (2026-11-02): se agregó captura de voz con `MediaRecorder`, envío multipart al endpoint canónico, errores recuperables, reintento idempotente y continuidad del historial voz/texto; se actualizaron documentación y tareas locales. Validación: suite completa (126 pruebas, 17 archivos) y build de Vite correctos; `git diff --check` sin errores. Limitación: no se hizo validación visual manual ni prueba con micrófono/backend real porque el control del navegador no pudo determinar con seguridad la URL de la pestaña.
- Contabilidad del taller (2026-11-02): se implementaron rutas protegidas por ADMIN, cliente API configurable, importes exactos con `BigInt`, alta balanceada con revisión e idempotencia, listado con filtros/paginación, detalle y reversión compensatoria según OpenAPI del backend. Se añadió enlace de navegación para ADMIN y adaptación móvil. Validación: suite completa con 162 pruebas aprobadas y build de Vite correcto; no se usaron datos financieros reales. La inspección manual visual quedó pendiente porque Computer Use detuvo la sesión al no poder confirmar con suficiente seguridad la URL del navegador; la validación de cuentas de cada rol requiere backend de pruebas. Contrato canónico en el repositorio backend `specs/003-asientos-contables/contracts/accounting.openapi.yaml`.
- Tickets administrativos del taller (2026-11-02): se conectaron Banco, alta y detalle con `VITE_API_URL` y las rutas ADMIN; se agregaron filtros/paginación completa, traducción de códigos, alta con adelanto, PATCH de estado, auditoría y cotización de solo lectura. El cliente de tickets del portal no cambió. Validación: suite completa (189 pruebas en 29 archivos) y build de Vite correctos; `git diff --check` sin errores de whitespace. E2E requiere aplicar la migración backend a una base desechable y la revisión visual a 360/390/768/1024 px y ambos temas queda pendiente.
- Compras a proveedores del taller (2026-11-03): se conectaron las vistas ADMIN de listado, detalle, registro, recepción idempotente y gestión de proveedores con `VITE_API_URL`; las líneas de catálogo conservan `spare_parts.id` como `spare_part_id` y el cliente bloquea el uso de inventario demo. Se añadieron importes exactos en centavos, estados en español y navegación responsive. Validación: análisis sintáctico de 11 módulos y build de Vite correctos. La validación manual con datos reales requiere backend de prueba con migración de compras aplicada, sesión ADMIN y `VITE_API_URL` configurada; la suite de pruebas no se ejecutó.
- Proveedores (2026-11-04): `SupplierManager` se reemplazó por `SupplierList` (listado con búsqueda, filtro por estado, desactivar con confirmación y reactivar) y `SupplierForm` (alta/edición en página propia, como Repuestos). Validación en `src/domain/suppliers.js`; los 422 del backend conservan su mensaje y campo, y el RUC repetido (409 sin campo) se marca en el RUC. Compras enlaza a Proveedores. Validación: 264 pruebas en 40 archivos y build correctos; flujo real contra backend local y PostgreSQL (alta, RUC duplicado, desactivar, filtrar inactivos, reactivar, editar) sin desborde a 360/390/1280 px. Luego se agregó `GET /api/admin/suppliers/{id}` en el backend y la edición por enlace directo lo usa. Limitación: a 768 px la franja de navegación del taller desborda por las pestañas Clientes y Ventas (previo a este cambio).
- Clientes y comercio frontend (2026-11-03): se conectaron clientes comerciales separados de cuentas, tickets con varias cotizaciones de servicio, cotizaciones de venta, pagos y ventas; el portal consulta por sesión y ADMIN tiene rutas protegidas para clientes y operaciones. Aceptar una oferta no se presenta como pago; la UI usa respuestas backend e IDs numéricos del inventario. Validación: 236 pruebas aprobadas en 37 archivos, build de producción correcto y `git diff --check` limpio. E2E y revisión visual dependen de las rutas y la resolución de customers en el backend Spec 007; no se operó sobre datos reales.
- Catálogo y consultas contables (2026-11-09): se añadieron vistas ADMIN para planes/cuentas, periodos y eventos, diario/mayor/balance con exportación CSV/XLSX; el alta de asientos elige cuentas del plan y conserva la lectura de snapshots históricos. Validación: `npm run build` correcto; `git diff --check` limpio. No se ejecutaron tests. Limitaciones: falta recorrido manual contra backend PostgreSQL de pruebas y revisión visual responsive/teclado/temas; el build reporta un chunk JavaScript mayor a 500 kB.
- Búsqueda de cuentas al crear asientos (2026-11-09): el selector ahora carga las primeras 50 cuentas activas, imputables y vigentes al elegir el plan, sin requerir texto; el campo acepta hasta 120 caracteres y hace búsqueda parcial remota por código o denominación. El backend y `multiagentedb` se consultaron directamente: hay coincidencias para consultas de código y nombre. Validación: build Vite y lectura del catálogo backend; no se ejecutaron pruebas ni recorrido de navegador con sesión ADMIN.
- Descripción por jerarquía contable (2026-11-09): al seleccionar una cuenta, la descripción de línea se rellena con `parent_name`; para cuentas raíz usa su propia denominación. El ADMIN puede editarla luego. El backend ya devuelve la cuenta padre en la respuesta de catálogo; el cambio es solo de interfaz. Validación: compilación Vite; falta comprobar la edición manual desde el navegador con sesión ADMIN.

- Ordenes de compra frontend (2026-11-09): se agregaron rutas ADMIN para listar, crear/editar, emitir, cancelar y recibir ordenes; las recepciones usan reintento idempotente y las facturas se vinculan durante el alta. Las pruebas automatizadas y la compilacion quedan pendientes en esta pasada.
